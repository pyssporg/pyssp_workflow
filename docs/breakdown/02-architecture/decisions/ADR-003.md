# ADR-003: This Repository Owns the Development Tree

**Status:** Accepted
**Layer:** architecture-decision

---

## Context

The capabilities this package composes (`pyssp_standard`, `pyssp_simulate`,
`pyssp_sysml2`, `pyssp_vv`, `sequence_extensions`) were each linked as a
submodule of `ssp_references`. Development therefore happened in a consumer
repository: every capability change needed a gitlink commit there, and there was
no single checkout from which the whole composition could be built and tested.

Only `pyssp-standard` is on PyPI. The rest are git-only, so the development
checkout remains the install mechanism for now.

## Decision

`pyssp_workflow` is the development tree. The five capabilities are linked under
`3rd_party/`, and `ssp_references` links this repository only.

- `.gitmodules` here pins the exact revision each capability was tested with.
  `pyssp_standard` stays detached on `architecture_review` and has no branch.
- Installation is explicit and split by constraint: `requirements-dev.txt`
  (standard, simulate, vv), `requirements-flow.txt` (Python 3.11+, flow engine),
  `requirements-sysml.txt` (CLI-only authoring environment).
- `pyproject.toml` keeps the `build`, `simulate`, and `flow` extras as reserved
  names. They gain versions with the first PyPI release; they are not a second
  install path today.
- Submodule URLs use HTTPS so `actions/checkout` can fetch them without a deploy
  key. Gitlinks, not branch tracking, define what CI runs.

## Consequences

- One clone produces the whole composition; `git submodule update --init
  --recursive` is the only setup step beyond `pip install -r`.
- Bumping a capability costs three commits: capability, this repository's
  gitlink, then the consumer's gitlink. That latency is accepted; it is the
  price of keeping each package separately versioned and published.
- A `pyssp_vv`-only developer clones this repository or clones `pyssp_vv`
  directly. The pin here does not restrict the capability's own releases.
- Physical nesting does not change the import rules. `pyssp_vv` still imports
  nothing from the ecosystem, `authoring` still cannot import `pyssp_vv`, and
  only `nodes`/`cli` may import `pyssp_vv.judge`.
- CI checks out recursively and installs `requirements-dev.txt`; without that,
  the suite would silently test a package that cannot import its capabilities.

## Alternatives considered

1. **Keep the flat layout in `ssp_references`.** Rejected: the consumer owns the
   development pins, so capability work and consumer work cannot be separated.
2. **A monorepo with packages instead of submodules.** Removes the three-commit
   hop and pin drift, but discards per-repository tags and release workflows.
   Deferred; the submodule shape preserves the option to publish each package
   independently.
3. **Declare git URLs in `pyproject.toml`.** Pip would clone its own copies,
   which diverges from the checked-out submodules and defeats reproducible
   local testing.
