# ADR-002: Explicit Path Addressing

**Status:** Accepted
**Layer:** architecture-decision

---

## Context

Consumers of the library are expected outside this repository: other projects
hold SSP models in their own layouts, and some will build flows over artifacts
produced elsewhere. The library must work without adopting a directory
convention, and node arguments must stay picklable for process pools.

Options considered:

1. Resolve `models/`, `artifacts/`, and a registry from a project root inside
   each function.
2. Accept explicit paths in every public function; provide a `Project` helper
   that supplies conventional paths as a convenience.
3. Accept either a path or an identifier resolved through an injected resolver.

## Decision

Adopt option 2.

- Every public function and node takes explicit paths for inputs and an
  explicit output directory.
- Outputs are derived from the assessment identifier *within the output
  directory*, never from the process working directory.
- A `Project` helper may compute conventional paths, but it returns plain paths
  and plain data. It holds no open handles and is never required.
- Functions return absolute paths; manifests relativise them on write.

## Rationale

- Option 1 makes every function working-directory sensitive and unusable for a
  consumer with a different layout.
- Option 3 creates two code paths and two failure modes for every call, and
  weakens picklability by requiring a resolver to travel with the call.
- Explicit paths make the artifact dependency graph visible at the call site,
  which is what makes a plan reviewable and a bundle complete.

## Consequences

- Signatures are longer. Paths are grouped into small frozen dataclasses
  (`Candidate`, `SimulationTarget`) rather than long positional lists.
- Every node's output location is predictable from its arguments, which is what
  makes "one node owns one output path" checkable.
- Callers must create and know their output directories; the library will create
  them but will not choose them.
